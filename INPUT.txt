A commit chain should each be functional and a value add.
1. Generally, I do cleanups and fixes first.
2. Then I do neutral refactors that set me up for success later (reorganizing code, renaming files, moving things around).
3. Then I do functional work.  Usually I aim for MVP, then parity, then feature add.

As such, let's reflect on this roadmap for this repo.

Web UI — Task Breakdown

**Done:**

- **Step 1: Functional — Live streaming via SSE.** `GET /api/sessions/{id}/stream` emits the session bus as Server-Sent Events; the chat page connects with HTMX's SSE extension (`sse-connect`/`sse-swap`) and streams message deltas, tool calls, and reasoning live. `/view` still serves the initial full-history render; `since` bridges the gap.
- **Step 2: Refactor — Server-local execution provider.** The server runs tools locally by default (`provider()` → `Dispatcher`) when no exec client is connected, and the web UI never registers as an exec provider. Verified by `TestSetProviderDefaultsToLocal` and a full no-client turn in `TestToolResultEnvelope`.

### Step 3: Functional — New chat button, no auto-create

UI-first: make creating a conversation explicit instead of implicit. No new API — `POST /api/sessions` already exists.

- **Remove auto-create in `handleIndex`.** Bare `GET /` currently creates a fresh session and 302s to `/?session=<id>`. Change it to render an empty state ("no session selected") — the page no longer manufactures a throwaway conversation you didn't ask for.
- **Add a New chat button** in the page header: a form `hx-post="/api/sessions"`; on success read the new session id from the JSON response and navigate to `/?session=<id>`. All client-side, no server change.
- What you get: an explicit way to start a chat, and the hook the sidebar (Step 4) points at.

### Step 4: Functional (UI) — Sidebar of sessions

Deliberately skip the `GET /api/sessions` list endpoint for now — the browser keeps its own registry.

- **Client-side session list.** The page records every session it creates or visits in `localStorage` (`porter.sessions`) and renders them as links to `/?session=<id>`, newest first, active one highlighted.
- **Layout** gets a left `<nav>` sidebar: New chat button on top, session list below, main chat area to the right. Still fine on mobile (sidebar collapses / stays minimal) since Step "mobile-responsive layout" is a later pass.
- **Why skip the API:** sessions are in-memory on the server anyway, so a client list is no worse than a server list until SQLite persists them. When the server grows a list endpoint (or persistent sessions land), swap the sidebar to server-rendered data with no UI change.

### Later steps (abstract)

- **Tool call/result display** — collapsible, syntax-highlighted, with timing and exit codes. Stream tool output live as it runs.
- **Reasoning display** — collapsible reasoning blocks, dimmed by default, expandable.
- **Cost/token display** — per-message, per-turn, per-session totals. Data is already on the bus (`KindTurnDone`); just needs rendering.
- **Fork/tree visualization** — conversation tree view, click to fork or rewind. Requires turn IDs in the history response and a tree rendering.
- **Connection status indicators** — show whether the SSE stream is connected, whether a turn is running, queue depth.
- **Mobile-responsive layout** — the README emphasizes "chat from any device." Fluid layout, touch-friendly input.
- **Auth** — single-user token, gate the whole UI behind it. Defer until the UI is useful.
- **Persistent sessions** — tie into the SQLite-backed history roadmap item so sessions survive server restarts.
